0. DOCUMENT PURPOSE
================================================================================

This document was developed as the operating build contract for using Fable/Claude
Code to turn the existing Remote Outpost prototype into a complete research-grade
2D behavioural assessment game.

The project uses two starting points:

1. Existing technical/game foundation
   - Phaser 3 + TypeScript + Vite.
   - Existing top-down Phaser RPG / Pokemon-like movement and scene foundation.
   - Existing Remote Outpost behavioural prototype work.
   - Existing EventLogger, SessionState, QualtricsBridge, DataQualityTracker,
     ScoringManager, and ResearchRuntime systems.
   - Existing branch:
       fable-final-game-prep-from-prototype
     created from:
       prototype/bfi-grit-behavioural-mapping

2. Production method inspired by Stardew-like/Fable game-building workflow
   - Spec-first implementation.
   - Connected 2D world.
   - Room-by-room build.
   - Clear definition of done.
   - PixelLab MCP for asset generation/polish.
   - Playwright/browser testing.
   - Autonomous build beats only after the specification and verification contract
     are explicit.

The target game is not a Stardew clone and not a new project from scratch. It is a
remote research outpost / expedition-station behavioural assessment, built on the
existing Phaser RPG top-down foundation and upgraded into a connected, coherent,
room-based game world.

================================================================================
1. NON-NEGOTIABLE SCIENTIFIC POSITION
================================================================================

The game is a behavioural analogue layer, not a questionnaire replacement.

The validated self-report scales remain in the Qualtrics survey. The game produces
event-log indicators that can be compared against those scales for convergent and
discriminant validation.

Primary source of truth:
  remote_outpost_MASTER_33_alignment_LOCKED_v0_2.xlsx

Secondary source of truth:
  remote_outpost_behavioural_blueprint_MASTER_corrected_v1_0.xlsx

Exact-item reference:
  remote_outpost_exact_33_item_list_ALIGNED_to_blueprint.xlsx

Core rules:
1. Q01-Q33 is the stable reference key.
2. All rooms, mini-games, event names, derived variables, and scoring rules must
   trace back to Q01-Q33 or be explicitly labelled as control/usability data.
3. Do not show validated questionnaire item wording in player-facing dialogue.
4. Do not collapse the behavioural output into one global “good player” score.
5. Compute separate subindices first:
   - organisation
   - productiveness
   - responsibility
   - prudence/carefulness
   - adaptive persistence
   - inappropriate persistence
   - optional goal-time preference / delayed-benefit proxy
6. Inappropriate Persistence is maladaptive. Higher values mean more blind or
   counterproductive persistence, not better persistence.
7. Goal-Time Preference is optional/exploratory. A short game cannot directly
   measure literal multi-year goal orientation.
8. Grit-S Consistency of Interest is partly weak/exploratory in a short game.
   Score return-to-task and unresolved non-return, not mere switching.
9. Q04 is cleanup/disorder. It must not be implemented as the old planning-before-
   acting construct.
10. Engineer Hub / NPC Report-Back is a priority module because it fills the
    responsibility/dependability gap without changing the persistence scoring model.

================================================================================
2. FINAL GAME CONCEPT
================================================================================

Working title:
  Remote Outpost Assessment

Setting:
  A remote research outpost / expedition station where critical systems must be
  stabilised before final core activation.

Player role:
  A newly arrived station assistant / field researcher who must inspect, repair,
  report, prepare, respond to warnings, manage interruptions, and finalize the
  outpost core.

Format:
  Short 2D top-down browser game.
  Approximate target playtime: 15-20 minutes for pilot; can be shortened for study.

Core player loop:
  move -> inspect -> choose action -> receive feedback -> revise/continue/skip ->
  task state updates -> events logged -> room outcome influences final core.

World structure:
  Dock / Arrival Bay
     -> Station Hub
        -> Archive Room
        -> Systems Repair Room
        -> Engineer Hub / NPC Report
        -> Inventory / Preparation Room
        -> Hazard Control Room
        -> Optional Side Repair Bay
        -> Interruption Corridor
        -> Final Core Room

Progression:
  The participant should experience the station as one connected world. Rooms may be
  implemented one-by-one, but the final game must connect all rooms into one flow.

No traditional RPG progression:
  Do not add money, shops, XP, skill levels, combat, stat boosts, power upgrades, or
  mechanics that change task difficulty across participants.

Allowed progress indicators:
  - mission checklist
  - active/unresolved objective tracker
  - station stability meter
  - non-power-changing badges/status labels
  - final core status board

- timestamp_ms
- elapsed_seconds
- room_id
- task_id
- study_item_ids

- object_id
- choice_value
- attempt_number
- previous_state
- new_state

- x
- y

3.3 Debug/runtime API
window.researchRuntime must remain available in dev/debug mode:
- printSummary()
- completeDebugSession()
- getEvents()
- printEvents()
- exportEventsJSON()

3.4 Qualtrics launch/return
The game must parse:
- participant_id
- game_session_id
- condition
- return_url
- game_version

The game must prepare/preview summary variables for Qualtrics without overwriting
raw logs.

3.5 UI systems
Required UI modules:
- dialogue box
- terminal panel
- checklist panel
- choice prompt
- status board
- active objective tracker
- final summary/debug panel
- optional PixelLab-polished UI skin later

3.6 Room/task abstraction
Each task should be implemented through a reusable pattern:
- enter room
- show objective
- interact with NPC/object
- present mini-game
- update task state
- log event
- update mission state
- update derived variables
- allow exit/return where appropriate
